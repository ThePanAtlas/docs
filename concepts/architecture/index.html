    Architecture¶

    panAtlas has two architectures that need to be kept apart: the target design (a git-backed, federated markdown fact-graph rendered to a static site) and what runs today (a build pipeline that compiles JSON registries and a property graph, served by a WordPress plugin). This page describes both, how data moves from acquisition to the site, and where each part runs.

    Read the flow left to right:

    1. Acquire. Each source has its own fetcher on the cluster that resumes, verifies every file, and writes a completion record only when the copy is complete (Acquisition).
    2. Register. A dataset gets a registry entry with a URN, licence and access class, and an audit manifest whose hash pins the exact version on disk (Dataset registry, Manifests). Fold and register scripts write it into web/datasets.json.
    3. Build. Heavy analysis runs on the cluster (document-to-concept mapping, embeddings, evaluation ingest). Its JSON outputs come to the repository, where the graph builders compile the served property graph and catalogs, and build_all.sh layers the curation passes on top and verifies the result (Build pipeline).
    4. Serve. deploy.sh copies the served JSON and the front-end assets to the plugin on the web host. The site reads static files at request time; nothing on the cluster is called by a page view.
    5. Query. The same graph is exported to RDF and loaded, with the OKN mirrors, into a SPARQL store on the cluster. Astral reaches the store; the public site exposes only the store's manifest (Knowledge store).

    Three properties follow from this shape:

    • The site is a reader of files. The WordPress database holds users, options and the audit log, not the atlas. The atlas is the JSON in the plugin's data/ directory plus large assets outside the web root.
    • The cluster is never on a page view's critical path. The only runtime call outside the web host is the Navigator and model lens to the hosted LLM endpoint. Astral's SPARQL and coverage tools are the exceptions on the agent side, and they go over a restricted SSH key, not an inbound port.
    • Two front doors with one data source. The plugin's REST routes and the Astral agent read the same files; the agent does not call WordPress (web/astral/atlas_store.py).

    The architecture pivot¶

    The first plan (PLAN_v1_wordpress.md, now history) built panAtlas as a WordPress application: custom post types for nodes and datasets, custom MySQL tables for edges and runs, WordPress roles, and a pre-write veto filter. On 2026-07-26 the owner replaced the substrate with a federated markdown graph on the Atlas model (ARCHITECTURE.md). The reason given is that a relational database behind an application server is single-tenant: it cannot be forked, diffed, merged, or split by community, so community-scoped facts cannot federate.

    WordPress plan Federated markdown design
    Custom post types (pa_node, pa_dataset, …) Typed markdown pages, one file per node
    Edge table Typed wikilink lists in frontmatter
    Runs table Out-of-graph append-only run store, plus verified result- summary pages
    WordPress roles and capabilities Git organisation and team membership, branch protection, CODEOWNERS
    Pre-write veto filter Linter in an editor hook and a required CI check on every pull request
    REST API on WordPress Static site (read), git pull requests (write), generated JSON (agents)
    ORCID via a WordPress plugin ORCID via OIDC on the git host

    The conceptual model survives unchanged: the curriculum graph, the jurisdiction-parameterised education ladder, the six stratification axes, the assessment framework, the provenance ethos, ORCID identity and Wikipedia seeding. PLAN.md (the current plan) builds on this decision and adds the two-layer design: a human-readable layer of concept and document pages and a machine-readable layer of atomic fact- and entity- pages (Graph schema).

    What actually runs today¶

    The pivot is a design decision, not a migration that has happened

    As of the repository at 57505c6 the live system is still a WordPress plugin serving JSON. Specifically:

    • WordPress serves the site. The panatlas-explorer plugin (version 0.2.2) registers the REST routes, shortcodes, roles and audit table; MySQL holds users and the panatlas_audit table.
    • The property graph is compiled from JSON registries and cluster outputs, not rendered from the markdown vault. web/build_layered.py reads the atlas/20-concepts/ pages for the concept spine; the remaining atlas/ page types (facts, entities, items) are not yet in the served graph.
    • No CI, git-host ORCID login, pull-request verification or static renderer exists in the repository. atlas/tools/lint_panatlas.py and atlas/tools/seed_wikipedia.py are the two built tools.
    • No page in atlas/ is verified.
    • Writes are proposals. POST /panatlas/v1/propose records a proposal in the audit log for a curator; it edits nothing.

    The graph standards adopted the same day (GRAPH_STANDARDS.md) describe the served graph.json as a projection of an RDF graph, not a separate source of truth. That RDF form now exists: web/rdf/build_rdf.py exports the served graph as N-Quads, and the SPARQL store holds it.

    Layers of the graph¶

    GRAPH_STANDARDS.md binds the representation to one RDF graph in three layers joined by concept IRIs: a terminology backbone, a multi-modal instance layer, and a working property graph (what the explorer renders). The standard was written for medicine, the domain built first, so it names the medical vocabularies (MeSH canonical, with SNOMED CT, LOINC, RxNorm, UMLS and ICD cross-codes) and FHIR R4 for clinical records; the served graph already grounds other domains in their own vocabularies, such as FoodOn for foods and Wikipedia for general concepts. LAYERS.md separates the same system differently, into substrate (identity), connectivity (claims) and embeddings (one registered model per modality). Both are explained in Layers; the vocabulary is in RDF vocabulary and the code systems in Code systems.

    Distributed by design¶

    panAtlas is built as a distributed system on the Cresco agent mesh. Datasets join the atlas where they sit, each managed by its own cresco-panatlas plugin instance at the hosting site, and only structure crosses the mesh. The hub on the web host pulls every manager's report, shows them in the Mesh view, and folds permitted contributions into the graph. Remote panAtlas instances and computational resources are treated the same way, as peers on the mesh.

    This documentation covers the mesh, federation contract, dataset managers, agents and operations in its own section, starting at Distributed.
