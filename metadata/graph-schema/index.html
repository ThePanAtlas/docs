    Graph schema¶

    This page documents every node type and every edge type in the panAtlas served graph, with the property keys each one carries and the script that writes it. Every count on this page was computed with python3 from the served graph file at repo HEAD 57505c6 on 2026-11-10. Nothing here is taken from a summary block or a design document unless the text says so.

    The served graph is web/wp-plugin/panatlas-explorer/data/graph.json. It is the property graph the explorer renders, the input to the RDF export (RDF vocabulary) and the input to the evaluation index behind the public API (Evaluation records). In the terms of GRAPH_STANDARDS.md it is layer 3, the "working / evidence property graph", which is a projection of the terminology backbone and the clinical instance layer. See Knowledge layers for how the layers relate.

    The stats block inside graph.json is stale

    graph.json carries a stats object, but several scripts rewrite parts of it and enrich_graph.py replaces it wholesale, so it no longer matches the file. At HEAD: stats.edges says 13,869 (the file has 17,119); stats.edges_by_rel has no entry for ten relations that exist (for example has_artifact_type, stage_trained_on, has_register); stats.layers reports concept 203, dataset 174, ontology 43; stats.concept_classes reports 44 model nodes (there are 90); and stats.curriculum.models_curriculum_undisclosed is 1 (36 model nodes carry curriculum_disclosed: false). Compute counts from nodes and edges, never from stats.

    File format¶

    graph.json is one JSON object with four keys:

    Key Type Content
    stats object Summary counters written by the build scripts (stale, see above) plus measured corpus figures such as footprint, documents_mapped and image_documents
    roots list ["atlas-root"], the entry node for navigation
    nodes list 6,187 node objects
    edges list 17,119 edge objects

    Node object¶

    Four keys are on every node: id, label, kind, layer. Every other key is optional and depends on the kind. The most widely used optional keys are:

    Key Nodes carrying it Meaning
    source 5,953 Free-text statement of where the node's content came from
    modality 5,701 text, structured, imaging-ct, imaging-ultrasound-rf, time-series, imaging-wsi, imaging, genomics, or an omics-* value
    concept_class 5,577 knowledge (5,252), evaluation (195), model (90), artifact-type (35), register (5)
    built_by 5,543 Free-text statement of the method that produced the node (for example "grounded to MeSH via UMLS UTS (resolver + adversarial audit + live confirmation)")
    desc 5,500 Description
    grounding 5,328 Which vocabulary grounds the node; see Controlled vocabularies
    canonical_id 5,013 Canonical identity, <prefix>:<code>; prefixes in use are mesh (3,390), foodon (1,558), wikipedia (24), fdc (24), panatlas (17)
    mesh_dui, mesh_name 3,400 MeSH descriptor UI and preferred name

    Edge object¶

    Every edge has exactly four required keys: from, to, rel, id. Some relations add attributes, listed per relation below.

    The edge id is content-addressed:

    "e-" + hashlib.blake2b(f"{from}|{to}|{rel}".encode(), digest_size=10).hexdigest()

    The same formula appears in enrich_graph.py, hygiene_enrich.py, build_curriculum.py and build_concept_remap.py, so rerunning a script adds no duplicate edges. 16,916 of the 17,119 edges match the formula. The other 203 are the covers_topic edges with basis: arxiv-lexalign, whose ids have the form e-arxiv-<MeSH UI>-<target id>.

    Two kinds named benchmark

    llm-benchmark (106) is a language-model benchmark from the benchmark registry (benchmarks_llm.json). benchmark (18) is an imaging benchmark: 10 CT benchmarks built by build_benchmark_nodes.py with layer: dataset, and 8 whole-slide-image benchmarks built by build_patho_evals.py and link_neuropath.py with layer: concept. Both are described on Benchmarks.

    Standards that govern the graph¶

    GRAPH_STANDARDS.md is the decision record, adopted 2026-07-26 and extended 2026-09-26. Its binding rules are summarised here with what the served graph does.

    Identity and grounding¶

    GRAPH_STANDARDS.md was written for medicine, the domain the atlas started with, so its grounding rules name medical vocabularies. The served graph applies the same idea to other domains with their own vocabularies (FoodOn and FoodData Central for foods, Wikipedia for general concepts; see Code systems). As written:

    • Every node must be tied to a real MeSH descriptor or another core concept (SNOMED CT or a UMLS concept). There are to be no orphan nodes.
    • A concept's canonical identity is its MeSH descriptor UI, for example mesh:D002309 for Cardiology. The MeSH UI is the deduplication key: two nodes with the same UI are the same concept.
    • MeSH is canonical over Wikipedia. Wikipedia is a readable overlay on a MeSH concept (an oldid attribute), never a second node. Wikipedia is the fallback identity only for non-MeSH, non-medical nodes, which may instead carry a Wikidata QID.
    • LAYERS.md restates the same rule as the substrate: identity is canonical_id, and two systems that emit the same canonical_id name the same entity without reconciliation.

    1,174 nodes carry no canonical_id

    The grounding rule is written for concepts, but it says "every node". At HEAD 1,174 nodes have no canonical_id: all 513 dataset, 172 food-category, 106 llm-benchmark, 90 model, 35 capability, 21 testing-type, 18 fhir, 18 benchmark, 15 authority, 14 training-stage, 13 capability-group, 9 eval-domain, 5 domain, 4 codebase, 3 guideline, 3 gen-category, 2 group, 2 system, 1 kg, 1 atlas-root and 1 eval-suite node, and also 118 concept and 10 disease nodes. The 118 concepts are the 117 Wikipedia-grounded general concepts that build_concept_remap.py creates with wiki_title and wp_url but no canonical_id (where build_layered.py would write wikipedia:<slug>), plus one corpus-classification concept. The 10 diseases are FoodAtlas diseases whose upstream id is OMIM, flagged with grounding: none and a grounding_note.

    Hierarchy and edge direction¶

    • The medical concept hierarchy comes from MeSH tree numbers. A descriptor's parent is the descriptor whose tree number is the immediate prefix. Specialties live in the MeSH H02 tree, diseases in C, techniques in E. In the served graph this hierarchy is the part_of relation with src: mesh_tree (3,360 edges); hand-curated links carry src: curated (1,845).
    • Backbone edges are SKOS-aligned. The property graph does not use SKOS names. The RDF export declares pa:partOf rdfs:subPropertyOf skos:broader and pa:related rdfs:subPropertyOf skos:related, and writes every code as skos:exactMatch. It writes no skos:narrower.
    • Edges point from the specific or owning node to the general or target node: a child is part_of its parent, a dataset covers a concept, a model is scored against a benchmark, a training stage follows the stage before it.

    GRAPH_STANDARDS.md does not state naming rules. The served graph follows these conventions consistently: kind values are lower case with hyphens; rel values are lower case snake case verb phrases; node ids are lower case, prefixed by kind (concept-, bench-, model-, dataset-, atype-, stage-), with MeSH expansion nodes as mesh-D<UI> and FoodAtlas nodes as fa-dis- and fa-food-. Identifier rules are on Identifiers.

    Provenance¶

    • Sources are evidence, not authority. Only panAtlas verification makes a fact verified, and a curator sign-off is recorded as verified_by.
    • FHIR-derived and vocabulary-derived assertions enter as evidence with provenance. Automatic MeSH groundings are adversarially verified, one agent per concept, each confirming the descriptor with a live UTS call, before they are trusted.
    • Every triple lives in exactly one named graph, and the named graph is its source of record. panAtlas curates only https://panatlas.net/graph/panatlas; mirrored graphs are read-only. See RDF vocabulary.
    • A dataset maintained elsewhere carries maintained_externally: true and a source_of_record block with the keys system, graph, agent, upstream_version, upstream_last_updated_on, held_version, endpoint, registry_file, registry_commit, funding, homepage, authoritative_namespaces, authoritative_declared. See Dataset registry.
    • LAYERS.md requires every edge to carry an origin (ontology-tree, curated, embedding-derived, agent-contributed) and evidence (for example {model, version, cosine}), so that connectivity merges as attributed claims.

    Edge provenance in the served graph is partial

    No edge in the served graph has an origin or an evidence attribute, and no node or edge has a verified_by attribute. Provenance is carried instead by src (5,715 edges), via (437), basis (216) and, for measured edges, n_docs, n, sim and acc. 10,863 edges carry none of src, via or basis. On nodes, provenance is the free-text source and built_by fields. The closest implementation of the contract is in the attach process (embed_attach.py and the local agent report, see Knowledge layers), which writes one nested attribute, claims: {origin: "embedding", model, version, cosine, canonical_id}, on its classified_as edges. Those edges are federation reports and are not in the served graph.

    Build order¶

    Each build script reads the served graph.json, changes it in place and writes it back. The ordered entry point is web/build_all.sh. Its stated precondition is that the upstream builders (build_graph.py, build_layered.py, build_all_datasets.py, build_train_sources.py, build_source_topics.py, sft_wiring.py, build_corpus_structure.py, model_wiring.py, build_benchmark_nodes.py, build_concept_remap.py, apply_bench_taxonomy.py) have already run. It then runs, in order:

    python3 build_artifact_types.py
python3 build_curriculum.py
python3 build_record_level.py
python3 pipeline/existing_meta/merge_gap.py || true
python3 build_existing_meta.py
python3 build_native_meta.py
python3 build_field_values.py
python3 build_patho_evals.py
python3 build_eval_map.py
python3 pipeline/check_curriculum_vault.py
node pipeline/ui_harness.js

    Scripts outside this sequence also write the graph: enrich_graph.py (measured_on, eval_accuracy), hygiene_enrich.py (grounded_in, contamination downgrades), attach_full_eval.py (model evaluation fields), reconcile_benchmarks.py, the link_*.py scripts and register_*.py fragments. No single script rebuilds the whole graph from scratch, so the order in which these were last run determines the file.
