    Dataset registry¶

    Status

    Built and in use. The registry is web/datasets.json (schema panatlas.datasets/1). Every count on this page was computed with python3 over the repository at HEAD 57505c6 (2026-10-31) by walking all web/datasets*.json files and enumerating every key path. Nothing here is projected. Field meanings come from the scripts that write and read each field; where no script defines a value set, the page says so.

    The registry is the authoritative list of datasets in the panAtlas federation. One entry describes one dataset, identified by its URN (Identifiers) and audited by its manifest (Manifests). Each entry is also the configuration source for that dataset's manager plugin (Dataset managers).

    Files and how they merge¶

    There are three kinds of registry file. They share one entry schema.

    File Role Entries at HEAD
    web/datasets.json The registry. Every registered dataset, each once. All tooling reads this file. 200
    web/datasets_*.json Fragments. A batch of entries produced by one acquisition or programme, kept beside the registry as the record of what that batch registered. 65 (subset of the 200)
    web/wp-plugin/panatlas-explorer/data/datasets.json The served catalog. The registry plus catalog-only entries and catalog-only fields, read by the site's Datasets view, the public API and the Astral assistant. 622

    A cluster-side copy of the registry also exists in <cluster project storage>/panatlas/datasets.json. It holds only the entries hosted on the HPC cluster that have managers (22 at first registration, 66 on 2026-09-17 per the project record). The hourly manifest refresh rewrites that copy, not the repository file; see Manifests.

    Fragments¶

    Every fragment URN is also in web/datasets.json; the union of all nine files is exactly the 200 registry URNs. Fragments are merged by upsert keyed on urn:

    • web/register_fragment.py <fragment.json> (general) and its predecessor web/register_tcga.py. New URNs are appended. For existing URNs the fragment entry replaces the registry entry, except that manifest and linked_nodes are kept from the registry when set, and, if the registry entry is already active, its status stays active and its acquisition.status, acquisition.finished and acquisition.summary are kept. The script then copies the fragment to web/<basename> (it never overwrites another fragment's copy) and asserts no duplicate URN.
    • The fold scripts (web/fold_manifests.py, web/fold_tcga_manifests.py, web/fold_renal_manifests.py) write manifest and status updates into web/datasets.json and into fragments that carry the dataset.

    Fragments drift from the registry

    At HEAD, 48 of 65 fragment entries are identical to their registry entries. The other 17 differ only in fields filled after registration: all 17 lack the acquisition key that the registry carries as {} (6 predictor-suite, 5 JK-Decide and 6 embedding-stack entries), and the 6 embedding-stack entries also have no manifest while the registry has one. Fragments are a historical record of a batch. Read web/datasets.json for current state.

    The fragment top-level block is meta with keys schema, description, host_default, root_default, measured, manifest_tool, models_registry, benchmark_field, subset, program, fragment, created, updated, acquisition_driver, acquisition_log, vault (each fragment carries a subset). One fragment, web/datasets_kos_v6.json, uses top-level schema and note instead of meta.

    Field reference¶

    How to read the tables. Present is the number of the 200 registry entries that carry the key (an entry whose value is null counts as present). Required means present in all 200; no JSON Schema enforces it, but every tool assumes it. Writes names repository scripts that set the field; "fragment" means the value arrives in a fragment produced outside this repository (on the cluster, or hand-written) and is merged by register_fragment.py. Reads names consumers. Every field is also copied into the served catalog by web/sync_catalog.py and into the RDF export where noted. public-api.php is web/wp-plugin/panatlas-explorer/includes/public-api.php; its /datasets/{slug} route serves only a fixed whitelist of fields (marked API).

    Strata axes. The registry has no top-level strata field. These name columns of that corpus's case manifest, not registry fields.

    Catalog-only entries and fields¶

    web/sync_catalog.py upserts every registry entry into the served catalog by URN. For URNs already in the catalog it replaces the entry with the registry entry but preserves the catalog-only fields listed below. For new URNs it appends the entry with those fields defaulted (desc from modality_detail, stage: dataset, used_in_training: false, dtype: benchmark if benchmark is truthy else source, part_of_corpus from part_of, vault_page from vault). At HEAD the 200 registry entries are identical in the catalog apart from these fields.

The public stats route counts datasets by status over the catalog, so its totals mix both vocabularies.

    used_in_training in two places

    used_in_training is a registry field (59 entries) and also in sync_catalog.py's list of catalog-only fields, so the catalog's existing value wins over a later registry change. At HEAD the two agree on all 59 entries.

    register_fragment.py, register_tcga.py, register_okn.py, register_openh.py, register_arxiv.py, register_neuropath.py and sync_catalog.py assert URN uniqueness before writing; the fold scripts, the linkers, apply_registry_licences.py and dataset_manifest.py do not (they never add entries). Writers use different JSON indentation (indent=1 or indent=2), so a diff of web/datasets.json after a run often shows whitespace changes on every line; compare parsed JSON, not text.
